# Backend Folder Reference

This document is the complete reference for the current `backend/` folder in the E-commerce project. It describes the folder layout, every source file, the database model, API routes, validation behavior, runtime dependencies, and the connection between the backend and the rest of the project.

The backend is a read-only FastAPI application for exposing the Olist e-commerce dataset and the verified Step 6 analytical extracts. It is an analytics and data-access API; it is not a shopping-cart, checkout, payment-processing, authentication, or customer-account system.

## 1. Backend at a glance

The backend is organized into four practical layers:

```text
HTTP client / frontend / API documentation
                 |
                 v
        FastAPI application (`main.py`)
                 |
                 v
     Versioned route modules (`api/v1/`)
                 |
        +--------+---------+
        |                  |
        v                  v
  SQLAlchemy sessions   Step 6 CSV extracts
        |                  |
        v                  v
       MySQL database   data/analytics/*.csv
```

- `main.py` creates the FastAPI application, registers routers, configures CORS, handles errors, adds security headers, and exposes health endpoints.
- `api/` contains HTTP dependencies and route handlers. Route handlers currently execute parameterized SQL directly through SQLAlchemy; there are no separate repository or service folders.
- `schemas/` contains Pydantic v2 response and shared validation models. These models define the public API contract and prevent internal database fields from leaking into responses.
- `models/` contains SQLAlchemy ORM mappings for the nine MySQL tables used by the project. The route modules mostly use direct SQL rather than querying these ORM classes.
- `database.py` loads the database URL, creates the SQLAlchemy engine and session factory, imports all ORM models into the metadata registry, and provides request-scoped sessions.

The source backend folder currently contains 19 Python source files, three source directories, and generated `__pycache__/` directories containing compiled `.pyc` files. The generated bytecode is not source code and is ignored by the project Git rules.

There are no `__init__.py` files in the current backend source tree. Python treats these directories as namespace packages, which works when the project root is the current directory and the application is started as `backend.main:app`. The relative imports in the source files depend on that package-style startup.

### Generated bytecode folders

The current checkout also contains these generated folders:

- `backend/__pycache__/`: compiled bytecode for `database.py` and `main.py`.
- `backend/api/__pycache__/`: compiled bytecode for `api/deps.py`.
- `backend/api/v1/__pycache__/`: compiled bytecode for the four versioned route modules.
- `backend/models/__pycache__/`: compiled bytecode for the ORM model modules and the namespace package cache.
- `backend/schemas/__pycache__/`: compiled bytecode for the five schema modules.

These folders contain Python interpreter cache files such as `*.cpython-314.pyc`. They speed up local imports but contain no independently maintained logic, configuration, API routes, database definitions, or documentation. They are covered by the project’s `__pycache__/` and `*.pyc` ignore rules and can be regenerated by Python.

## 3. File-by-file reference

### 3.1 `backend/main.py`

`main.py` is the application entry point. It creates the `FastAPI` object named `app` and is the module passed to Uvicorn.

It contains:

- Application metadata:
  - title: `Olist E-commerce Analytics API`
  - version: `1.0.0`
  - description: read-only catalog and analytics API for the Olist dataset.
- Router registration:
  - `catalog_router` under `/api/v1`
  - `customers_router` under `/api/v1`
  - `orders_router` under `/api/v1`
  - `analytics_router` under `/api/v1`
- CORS configuration from `ALLOWED_ORIGINS`.
  - Default origins are `http://localhost:3000` and `http://127.0.0.1:8000`.
  - Only `GET` is allowed.
  - `Content-Type` and `Accept` are the allowed headers.
  - Credentials are disabled.
- A shared `_error_response()` helper that creates the public `{ "error": { ... } }` response shape.
- Exception handlers for:
  - `HTTPException`: maps common statuses to `NOT_FOUND`, `VALIDATION_ERROR`, and `DATABASE_UNAVAILABLE`.
  - `RequestValidationError`: returns a concise 422 response and identifies the first invalid field.
  - `SQLAlchemyError`: logs the server-side database error and returns a safe 503 response.
  - unexpected `Exception`: logs the error and returns a safe 500 response.
- HTTP security-header middleware:
  - `X-Content-Type-Options: nosniff`
  - `X-Frame-Options: DENY`
  - `Referrer-Policy: no-referrer`
- `GET /`: simple application greeting.
- `GET /health`: verifies database connectivity and returns `HealthResponse`; it returns 503 if the database check fails.
- `GET /health/database`: runs `SELECT 1`, measures latency, and returns `DatabaseHealthResponse` with either `ok` or `unavailable`.

The application is intentionally read-only. No route in this file or the registered route modules performs INSERT, UPDATE, DELETE, or schema migration work.

### 3.2 `backend/database.py`

`database.py` owns database configuration and SQLAlchemy session lifecycle.

It contains:

- `load_dotenv()` to load the project `.env` file.
- `DATABASE_URL`, read from the environment. Importing the module raises `RuntimeError` if it is missing.
- Explicit imports of `Base` and all nine ORM model classes. This is required so every table is registered in `Base.metadata` even though `models/` is a namespace package without an `__init__.py`.
- One SQLAlchemy `engine` created with:
  - the configured `DATABASE_URL`;
  - `pool_pre_ping=True`, which checks stale pooled connections before use;
  - `pool_recycle=1800`, which recycles pooled connections after 30 minutes.
- `SessionLocal`, a shared `sessionmaker` with `autoflush=False`, `autocommit=False`, and `expire_on_commit=False`.
- `get_db()`, a generator dependency that creates one session, yields it, and always closes it.
- `check_database_connection()`, which runs `SELECT 1` and returns `True` when successful without exposing connection details.

The module does not create tables. The MySQL schema and data must already exist before the API starts successfully.

### 3.3 `backend/api/deps.py`

`deps.py` provides reusable FastAPI dependencies for route modules.

It contains `database_session()`, a thin wrapper around `database.get_db()`. Route functions depend on this generator to receive a SQLAlchemy `Session` and to get automatic cleanup after the request.

This indirection gives route modules a stable dependency name and keeps session lifecycle behavior in one place.

### 3.4 `backend/api/v1/catalog.py`

`catalog.py` defines the catalog router with the `catalog` tag. It uses direct, parameterized SQL through `sqlalchemy.text()` and converts rows into catalog schemas.

Shared helpers:

- `_not_found(resource, identifier)` creates consistent 404 errors.
- `_pagination(...)` runs a count query and returns validated `PaginationMeta`.
- `DatabaseSession` is an annotated dependency alias for a request-scoped SQLAlchemy session.

Routes:

| Route | Purpose | Filters / pagination |
|---|---|---|
| `GET /api/v1/products` | Lists products and translated category names. | `limit`, `offset`, `category_name`, `category_name_english` |
| `GET /api/v1/products/{product_id}` | Returns one product. | Product ID path parameter |
| `GET /api/v1/sellers` | Lists sellers. | `limit`, `offset`, `state`, `city` |
| `GET /api/v1/sellers/{seller_id}` | Returns one seller. | Seller ID path parameter |
| `GET /api/v1/category-translations` | Lists category translations. | `limit`, `offset`, `category_name`, `category_name_english` |
| `GET /api/v1/category-translations/{product_category_name}` | Returns one translation. | Category name path parameter |
| `GET /api/v1/geolocation` | Lists representative ZIP-prefix geolocation rows. | `limit`, `offset`, `state`, `city` |
| `GET /api/v1/geolocation/{zip_code_prefix}` | Returns one geolocation row. | ZIP prefix path parameter |

List routes use deterministic ordering, bound SQL parameters, a data query, and a separate count query. Detail routes return 404 when no matching row exists. Internal model flags and fields are not selected unless the public response schema needs them.

### 3.5 `backend/api/v1/customers.py`

`customers.py` defines customer routes and calculates customer-level metrics from MySQL.

Routes:

- `GET /api/v1/customers`
  - Returns paginated customer records.
  - Supports `limit`, `offset`, `customer_unique_id`, and `zip_code_prefix`.
  - Uses `customer_unique_id` as the person-level identity while retaining each source `customer_id` record.
- `GET /api/v1/customers/{customer_unique_id}`
  - Returns all matching customer records plus calculated metrics.
  - Metrics include order count, item count, item revenue, freight, payment total, first and last purchase, recency, and repeat-customer status.
  - Recency is calculated relative to `2018-08-28`, the analysis reference date used by the current implementation.
  - Returns 404 when the person-level customer does not exist.
- `GET /api/v1/customers/{customer_unique_id}/orders`
  - Reuses the order-listing logic to return the customer’s orders.
  - Supports `limit`, `offset`, `start_date`, and `end_date`.

The module uses parameterized SQL joins between `customers`, `orders`, `order_items`, and `payments`. It imports `list_orders` from `orders.py` so customer order results use the same order summary and pagination behavior.

### 3.6 `backend/api/v1/orders.py`

`orders.py` defines order summary and order detail endpoints.

It contains:

- A reusable `ORDER_SUMMARY_SQL` query that joins orders to customers and uses independent item and payment subqueries. The subqueries prevent item and payment joins from multiplying monetary totals.
- `_not_found(order_id)` for consistent 404 responses.
- `_filters(...)` for optional status, customer, and date-range conditions.
- `_summary(row)` for converting a database row into `OrderSummaryResponse`.

Routes:

- `GET /api/v1/orders`
  - Returns paginated order summaries.
  - Optional filters: `order_status`, `customer_unique_id`, `start_date`, and `end_date`.
  - Sorting: `sort_by=purchase_date|total_value` and `sort_order=asc|desc`.
  - Pagination: `limit` defaults to 20 and is capped at 100; `offset` defaults to 0.
- `GET /api/v1/orders/{order_id}`
  - Returns one order summary plus nested items, payments, and reviews.
  - Nested queries are ordered by item ID, payment sequence, and safe review record ID.
  - The response schema verifies that every nested row belongs to the parent order.
  - Returns 404 when the order does not exist.

Order money is exposed as BRL fields: `item_revenue_brl`, `freight_collected_brl`, `payment_total_brl`, `price_brl`, `freight_value_brl`, and `payment_value_brl`.

### 3.7 `backend/api/v1/analytics.py`

`analytics.py` defines the `/api/v1/analytics` router. It has two data sources:

1. Live, parameterized MySQL aggregation for summary, monthly sales, and category performance.
2. Verified Step 6 CSV extracts under the project-level `data/analytics/` directory for RFM, cohort, delivery, and CLV transaction routes.

`DATA_DIR` is calculated from the module location as the project root’s `data/analytics` folder. The required extract files are:

- `rfm_step6.csv`
- `cohort_retention_step6.csv`
- `delivery_metrics_step6.csv`
- `clv_transactions_step6.csv`

Helpers:

- `_read_csv(name)` loads a UTF-8 CSV into dictionaries.
- `_page(items, page)` slices an in-memory list and creates `PaginationMeta`.

Routes:

| Route | Data source | Behavior |
|---|---|---|
| `GET /api/v1/analytics/summary` | MySQL | Delivered-order count, customers, repeat customers, item revenue, freight, payments, and date range. |
| `GET /api/v1/analytics/monthly-sales` | MySQL | Delivered sales grouped by purchase month; optional `start_month` and `end_month`. |
| `GET /api/v1/analytics/rfm` | `rfm_step6.csv` | Optional segment and minimum score filters, sorted by score, paginated. |
| `GET /api/v1/analytics/cohorts` | `cohort_retention_step6.csv` | Optional cohort month and maximum month number. |
| `GET /api/v1/analytics/delivery` | `delivery_metrics_step6.csv` | Optional minimum and maximum delivery days, sorted longest first, paginated. |
| `GET /api/v1/analytics/categories` | MySQL | Top delivered categories by revenue or item count. |
| `GET /api/v1/analytics/transactions` | `clv_transactions_step6.csv` | Transaction-grain CLV inputs with customer/date filters and pagination. |

The transaction endpoint exposes inputs for CLV analysis; it does not claim to calculate predictive customer lifetime value. All SQL uses bound parameters except the small, explicitly constrained ordering fragments selected from `Literal` values.

### 3.8 `backend/models/base.py`

Defines `Base`, the SQLAlchemy `DeclarativeBase` superclass inherited by every ORM model. `Base.metadata` is the registry used by tests and database tooling to discover the nine mapped tables.

### 3.9 `backend/models/category_translation.py`

Maps the `category_translation` table through `CategoryTranslation`.

- Primary key: `product_category_name`.
- Data: source category name and optional English category name.

It supports catalog translation lookups and category labels in product and analytics responses.

### 3.10 `backend/models/customer.py`

Maps `customers` through `Customer`.

- Primary key: `customer_id`.
- Indexed person-level identity: `customer_unique_id`.
- Optional location: ZIP prefix, city, and state.

`customer_id` identifies an order-linked record; `customer_unique_id` is used for person-level analysis and repeat-customer calculations.

### 3.11 `backend/models/geolocation.py`

Maps `geolocation` through `Geolocation`.

- Primary key: `geolocation_zip_code_prefix`.
- Optional latitude, longitude, city, and state.

The project uses representative ZIP-prefix geolocation data rather than a full address or user-location service.

### 3.12 `backend/models/order.py`

Maps `orders` through `Order`.

- Primary key: `order_id`.
- Indexed foreign-key-like field: `customer_id`.
- Indexed status: `order_status`.
- Lifecycle timestamps: purchase, approval, carrier delivery, customer delivery, and estimated delivery.
- Source timestamps retained for auditability: `source_order_approved_at`, `source_order_delivered_carrier_date`, and `source_order_delivered_customer_date`.
- Data-quality and analysis fields: date correction flags/reasons, missing approval flag, analysis approval timestamp, imputation flag, and imputation method.

The model preserves both source and prepared/analysis values so the data pipeline can distinguish original data from approved corrections.

### 3.13 `backend/models/order_items.py`

Maps `order_items` through `OrderItem`.

- Composite primary key: `(order_id, order_item_id)`.
- Indexed references: `product_id` and `seller_id`.
- Optional shipping limit timestamp.
- Optional `price` and `freight_value` numeric values.
- `freight_zero_value_flag` for prepared-data auditing.

The composite key is required because one order can contain multiple item rows.

### 3.14 `backend/models/payment.py`

Maps `payments` through `Payment`.

- Composite primary key: `(order_id, payment_sequential)`.
- Optional payment type, installment count, and value.
- `payment_zero_value_flag` for prepared-data auditing.

The sequence number allows multiple payment records for one order.

### 3.15 `backend/models/product.py`

Maps `products` through `Product`.

- Primary key: `product_id`.
- Category name.
- Name and description lengths.
- Photo count.
- Weight and dimensions.
- Product-attribute optional/imputation flags and method.
- Missing-category flag.

The public catalog schema deliberately exposes product attributes but not the internal preparation flags.

### 3.16 `backend/models/review.py`

Maps `reviews` through `Review`.

- Safe primary key: `review_record_id`.
- Source `review_id`, which is indexed but not treated as unique because it can repeat in this dataset.
- Indexed `order_id`.
- Review score, optional comments, creation timestamp, and answer timestamp.
- Optional-comment and repeated-ID preparation flags.

Using `review_record_id` prevents duplicate source `review_id` values from violating the ORM identity model.

### 3.17 `backend/models/seller.py`

Maps `sellers` through `Seller`.

- Primary key: `seller_id`.
- Optional ZIP prefix, city, and state.

It supports seller list/detail catalog routes and order-item seller references.

### 3.18 `backend/schemas/common.py`

Defines shared Pydantic v2 models:

- `APIModel`: enables `from_attributes=True` and rejects undeclared fields with `extra="forbid"`.
- `PageParams`: `limit` 1–100, default 20; `offset` non-negative, default 0. Boolean values are explicitly rejected even though Python treats booleans as integers.
- `DateRangeParams`: optional `start_date` and `end_date`, requiring chronological order.
- `PaginationMeta`: total, limit, offset, and returned counts; validates that returned rows do not exceed the requested limit or total.
- `ErrorDetail`: public error code, message, and optional field.
- `ErrorResponse`: wraps `ErrorDetail` under the `error` key.

These types provide the common contract used across customer, order, catalog, analytics, and application-level error responses.

### 3.19 `backend/schemas/catalog.py`

Defines catalog response models:

- `ProductResponse` and `PaginatedProductResponse`.
- `SellerResponse` and `PaginatedSellerResponse`.
- `CategoryTranslationResponse` and `PaginatedCategoryTranslationResponse`.
- `GeolocationResponse` and `PaginatedGeolocationResponse`.

The models trim text identifiers and labels, constrain lengths and non-negative numeric attributes, constrain geographic coordinates to valid latitude/longitude ranges, and require geolocation latitude and longitude to be supplied together.

### 3.20 `backend/schemas/customer.py`

Defines:

- `CustomerSummaryResponse`: customer identity and location fields.
- `CustomerMetrics`: order/item counts, BRL metrics, purchase dates, recency, and repeat flag. The repeat flag must equal `order_count > 1`.
- `CustomerDetailResponse`: person-level ID, source customer records, and metrics.
- `PaginatedCustomerResponse`: customer rows plus pagination metadata.

Customer identifiers and city text are trimmed before length validation.

### 3.21 `backend/schemas/order.py`

Defines:

- `_clean_identifier()`: trims identifiers and rejects empty strings.
- `OrderSummaryResponse`: order/customer identity, status, lifecycle dates, and independently aggregated financial totals.
- `OrderItemResponse`: item, product, seller, shipping, price, and freight fields.
- `PaymentResponse`: payment sequence, type, installments, and value.
- `ReviewResponse`: review identity, score, comments, and timestamps.
- `OrderDetailResponse`: order summary plus item, payment, and review lists. It verifies all nested rows use the parent order ID.
- `PaginatedOrderResponse`: order summaries plus pagination metadata.

Order milestone dates cannot precede the purchase timestamp. Review scores are restricted to 1–5, and monetary values are non-negative.

### 3.22 `backend/schemas/analytics.py`

Defines response contracts for health and analytical data:

- `HealthResponse` and `DatabaseHealthResponse`.
- `AnalyticsSummaryResponse`: delivered-order counts, customer counts, BRL totals, and observation dates.
- `MonthlySalesResponse`: month, order/customer counts, item revenue, freight, and combined value.
- `RFMResponse` and `PaginatedRFMResponse`: customer RFM values, component scores, total score, and one of four descriptive segments.
- `CohortRetentionResponse`: cohort month, month number, cohort size, retained customers, and percentage.
- `DeliveryMetricResponse` and `PaginatedDeliveryMetricResponse`.
- `CategoryPerformanceResponse`.
- `CLVTransactionResponse` and `PaginatedCLVTransactionResponse`.

Cross-field validators ensure aggregate counts are logical, monthly combined values include both components, RFM totals equal component scores, retained customers do not exceed cohort size, delivery dates do not precede purchase dates, and pagination counts match returned item counts.

## 4. Database architecture and relationships

The backend expects the `ecommerce` MySQL database and these nine tables:

```text
customers.customer_id
        |
        +--> orders.customer_id
                 |
                 +--> order_items.order_id
                 +--> payments.order_id
                 +--> reviews.order_id

order_items.product_id --> products.product_id
order_items.seller_id  --> sellers.seller_id
products.product_category_name --> category_translation.product_category_name
customers/sellers ZIP prefixes --> geolocation.geolocation_zip_code_prefix
```

The relationships are represented as query joins and indexed/key fields. The current ORM models do not declare SQLAlchemy `relationship()` properties; the route SQL explicitly joins the tables.

Important business rules:

- `customer_id` identifies the source customer record associated with an order.
- `customer_unique_id` identifies the person across potentially multiple customer records.
- Delivered orders (`order_status = 'delivered'`) are the eligible population for realized-sales and most analytics.
- Item revenue, freight, and payment totals remain separate measures.
- Money is represented as BRL at the API boundary.
- Order items use `(order_id, order_item_id)` as their key.
- Payments use `(order_id, payment_sequential)` as their key.
- Reviews use `review_record_id`, not source `review_id`, as the safe key.

## 5. Connection to the rest of the project

### Configuration

The backend reads `DATABASE_URL` from the project root `.env` file. The project provides `.env.example` with this shape:

```text
DATABASE_URL=mysql+pymysql://user:password@localhost:3306/ecommerce
ALLOWED_ORIGINS=http://localhost:3000,http://127.0.0.1:8000
```

`APP_NAME`, `APP_VERSION`, and `DEBUG` are documented in the example file but the current `main.py` uses its own hard-coded title and version.

### Data preparation and analytics pipeline

The upstream data flow is:

```text
data/raw/
    -> Python/step3_prepare_data.py
data/prepared/
    -> manual MySQL import
MySQL ecommerce tables
    -> Python/run_post_load_pipeline.py
data/analytics/*.csv
    -> backend/api/v1/analytics.py
API responses
    -> frontend, Swagger clients, or other consumers
```

The backend does not prepare raw files, import CSV files, run the post-load pipeline, or refresh Power BI. The repeatable future-batch procedure is documented in [future_batch_data_runbook.md](./future_batch_data_runbook.md). That runbook explains how to append a future batch, run the post-load pipeline, validate outputs, and refresh [Reports/Overview.pbix](../Reports/Overview.pbix).

The backend’s extract-backed analytics routes depend on these project files:

- [data/analytics/rfm_step6.csv](../data/analytics/rfm_step6.csv)
- [data/analytics/cohort_retention_step6.csv](../data/analytics/cohort_retention_step6.csv)
- [data/analytics/delivery_metrics_step6.csv](../data/analytics/delivery_metrics_step6.csv)
- [data/analytics/clv_transactions_step6.csv](../data/analytics/clv_transactions_step6.csv)

The live SQL routes depend on the MySQL tables populated from the prepared files in `data/prepared/`. The backend does not write back to those data locations.

### Tests

Backend verification is outside the `backend/` folder in [tests/test_backend_basic.py](../tests/test_backend_basic.py). The test module imports the app, database metadata, route functions, and schemas to verify:

- database connectivity;
- all nine mapped tables;
- catalog, customer, and order pagination/detail behavior;
- analytical totals and extract-backed outputs;
- OpenAPI route registration;
- 404 behavior.

## 6. API response and error behavior

Successful responses are JSON and are validated by the declared Pydantic response model. Common error shapes are:

```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "Resource was not found",
    "field": null
  }
}
```

The application uses these main statuses:

| Status | Meaning |
|---:|---|
| 200 | Successful read operation |
| 404 | Requested customer, order, product, seller, translation, or geolocation record does not exist |
| 422 | Invalid path or query parameters, including pagination/date/model validation failures |
| 503 | Database is unavailable or a SQLAlchemy operation fails |
| 500 | Unexpected server-side error |

Database errors and stack traces are logged server-side but are not returned to API clients.

## 7. Run the backend

Run all commands from the project root, not from inside `backend/`, because the package imports and analytics path resolution assume the project root is on `PYTHONPATH`.

### 7.1 Prerequisites

1. Start MySQL.
2. Make sure the `ecommerce` database and all nine tables exist.
3. Create a local `.env` with a valid `DATABASE_URL`.
4. Use the project virtual environment and installed packages from [requirements.txt](../requirements.txt).
5. Ensure the Step 6 CSV files exist under `data/analytics/` before calling extract-backed analytics routes.

### 7.2 Start with Uvicorn

Using an activated virtual environment:

```powershell
cd C:\Users\mukth\OneDrive\Desktop\E-commerce

```

Using the project interpreter directly:

```powershell
cd C:\Users\mukth\OneDrive\Desktop\E-commerce
& .\.venv\Scripts\python.exe -m uvicorn backend.main:app --reload
```

### 7.6 Troubleshooting

- `Set DATABASE_URL...`: create `.env` in the project root or set the environment variable before starting Uvicorn.
- `Database unavailable`: check that MySQL is running, the host/port/database are correct, and the credentials work.
- CSV file not found for analytics: run the post-load pipeline described in [future_batch_data_runbook.md](./future_batch_data_runbook.md), then confirm the files under `data/analytics/`.
- Import errors when starting: start from `C:\Users\mukth\OneDrive\Desktop\E-commerce` and use `backend.main:app`; do not run `main.py` as a standalone script.
- CORS errors from a frontend: add the frontend origin to `ALLOWED_ORIGINS` as a comma-separated value.

## 8. Current limitations and operational boundaries

- Authentication and authorization are not implemented. Add them before exposing the API outside a trusted development/reporting network.
- The API is read-only and does not manage carts, checkout, payment capture, or user accounts.
- The backend does not run database migrations or create tables.
- The backend does not automatically load raw/prepared data or refresh Power BI.
- RFM, cohort, delivery, and CLV transaction endpoints load CSV extracts into memory per request. This is appropriate for the current reduced dataset but may require a database-backed or cached implementation for larger data volumes.
- The CLV endpoint exposes transaction inputs, not a predictive CLV model.
- The current code uses direct SQL in route modules. There are intentionally no `repositories/` or `services/` folders.
- Generated `__pycache__/` folders and `.pyc` files are local Python bytecode artifacts; they should not be edited or relied on as application source.

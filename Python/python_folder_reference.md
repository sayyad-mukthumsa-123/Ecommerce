# Python Folder Reference

This document describes the complete current contents of the project’s [Python/](../Python/) folder. It explains the purpose of each folder and file, what each file contains, why it exists, what it reads and writes, how the files connect to one another, and the commands used to run the repeatable Python workflows.

The folder contains the project’s exploratory notebooks, the repeatable preparation script, and the repeatable post-MySQL analytics pipeline. It is the processing layer between [data/](../data/), MySQL, the FastAPI backend, and the Power BI report.

## 1. Python folder architecture

```text
Python/
├── pre-analysis.ipynb
├── Pre-processing.ipynb
├── step3_prepare_data.py
├── step6_post_load_analysis.ipynb
├── run_post_load_pipeline.py
├── .ipynb_checkpoints/
│   ├── pre-analysis-checkpoint.ipynb
│   └── Pre-processing-checkpoint.ipynb
└── __pycache__/
    └── run_post_load_pipeline.cpython-314.pyc
```

The intended processing flow is:

```text
data/raw/
    |
    +--> pre-analysis.ipynb          exploratory profiling
    |
    +--> Pre-processing.ipynb        validation and preparation design
    |
    +--> step3_prepare_data.py       repeatable prepared-file generation
                                      |
                                      v
                              data/prepared/
                              data/quality/
                                      |
                              manual MySQL append
                                      |
                                      v
                              MySQL ecommerce database
                                      |
                                      v
                         run_post_load_pipeline.py
                         or step6_post_load_analysis.ipynb
                                      |
                                      v
                              data/analytics/
                                      |
                    FastAPI backend and Power BI report
```

The production-style repeatable path is `step3_prepare_data.py` followed by the manual MySQL load and then `run_post_load_pipeline.py`. The notebooks provide exploration, investigation, visual analysis, and an interactive version of the analytical work.

## 2. Folder and generated-artifact details

### `Python/`

The root contains all maintained Python scripts and notebooks. Scripts resolve paths from their own location, so they can be launched from the project root without depending on the current working directory. The notebooks use relative paths such as `../data/...` and are intended to be opened or run with the notebook located in this folder.

### `Python/.ipynb_checkpoints/`

This is a Jupyter-generated checkpoint directory. It currently contains checkpoint copies of `pre-analysis.ipynb` and `Pre-processing.ipynb`.

Checkpoint files exist for notebook recovery and autosave. They are not separate processing stages, should not be treated as authoritative source files, and may differ slightly from the active notebooks. The active notebooks are the files in the Python folder root.

### `Python/__pycache__/`

This is Python’s generated bytecode cache directory. It currently contains `run_post_load_pipeline.cpython-314.pyc`.

The `.pyc` file is generated from the post-load script to speed imports. It is not maintained source, does not define a separate workflow, and can be regenerated by Python. It should not be edited or documented as an independent implementation.

## 5. `step3_prepare_data.py`

### Purpose

`step3_prepare_data.py` is the repeatable Step 3 preparation script. It creates MySQL-ready copies of the raw data without modifying the immutable raw files.

It is the preferred command-line preparation workflow for future batches when the existing preparation rules should be applied consistently.

### Path configuration

The script calculates:

- `PROJECT_ROOT`: the E-commerce project root, one directory above `Python/`.
- `RAW_DIR`: `data/raw/olist_trimmed_1500_relational`.
- `PREPARED_DIR`: `data/prepared`.
- `QUALITY_DIR`: `data/quality`.

It creates `PREPARED_DIR` and `QUALITY_DIR` if they do not already exist.

### Main functions and data structures

- `APPROVED_APPROVAL_IMPUTATIONS`: an explicit mapping for the one approved missing approval timestamp. It retains the source null and populates only the derived analysis value.
- `read_csv(filename, dtype=None)`: reads a source CSV from `RAW_DIR`, optionally forcing identifier and ZIP columns to pandas string type.
- The script loads orders, customers, items, payments, reviews, products, sellers, categories, and geolocation into pandas DataFrames.

### Preparation logic

The script performs these operations:

1. Reads IDs and ZIP prefixes as strings so identifiers remain text and leading zeroes are not lost.
2. Converts product count fields to nullable integers rather than writing values such as `33.0`.
3. Adds product-attribute flags.
4. Imputes missing product name length, description length, and photo count using the approved prepared-subset medians:
   - `product_name_lenght`: 52
   - `product_description_lenght`: 555
   - `product_photos_qty`: 1
5. Records the imputed rows and method in product audit columns.
6. Parses order, shipping, review-creation, and review-answer dates.
7. Copies original order timestamps into `source_*` audit columns before correction.
8. Adds order approval missingness, imputation, and date-correction flags.
9. Applies the approved approval timestamp only to `order_approved_at_for_analysis`.
10. Corrects carrier dates that precede approval by setting them to the analysis approval timestamp.
11. Corrects customer delivery dates that precede carrier hand-off by setting them to the carrier timestamp.
12. Records the correction reason for every corrected row.
13. Adds `product_category_missing_flag`.
14. Marks review comments as optional with `review_comment_optional_flag`.
15. Preserves valid zero payment values and zero freight values and records flags for them.
16. Adds sequential `review_record_id` values because source `review_id` can repeat.
17. Adds `review_id_repeated_flag`.
18. Converts binary flags to integer values so they import cleanly into MySQL.

### Files written

The script writes:

- `data/prepared/orders_prepared.csv`
- `data/prepared/customers_prepared.csv`
- `data/prepared/order_items_prepared.csv`
- `data/prepared/payments_prepared.csv`
- `data/prepared/reviews_prepared.csv` in the script’s output mapping; the current checked-in file is named `reviews_prepared_mysql_binary.csv` from the controlled import workflow.
- `data/prepared/products_prepared.csv`
- `data/prepared/sellers_prepared.csv`
- `data/prepared/category_translation_prepared.csv`
- `data/prepared/geolocation_prepared.csv` in the script’s output mapping; the current checked-in file is named `geolocation_prepared_mysql_normalized.csv` from the controlled import workflow.
- `data/quality/date_corrections.csv`
- `data/quality/step3_preparation_summary.csv`

The script uses `NULL` as the no-quote null marker for orders because nullable order DATETIME fields must import as SQL `NULL` through the current MySQL Workbench workflow. Other files use `\\N` as their null marker.

### Why it is needed

This script provides a deterministic, auditable preparation process. It prevents accidental raw-file edits, preserves source values, creates approved analysis fields, makes key edge cases explicit, and produces files that can be imported into the `ecommerce` MySQL database.

### Important boundary

The script does not load MySQL. It only writes prepared files and quality artifacts. The MySQL append remains a controlled manual hand-off described in [future_batch_data_runbook.md](./future_batch_data_runbook.md).

### Why it is needed

This notebook documents the analytical method interactively and supports exploratory review of the current data. It is useful for understanding the calculations and visually checking outputs. For a repeatable future-batch refresh after MySQL loading, use `run_post_load_pipeline.py` instead.

### Analytical rules

- Delivered orders are the eligible population for realized sales, retention, and delivery analysis.
- Item and payment totals are aggregated separately before joining.
- Customer analysis uses `customer_unique_id` for person-level identity.
- RFM is descriptive and uses four-point component scores.
- Cohorts are based on the first delivered purchase month.
- Delivery duration is measured from purchase to customer delivery.
- CLV output is transaction-level input data only; no probabilistic/predictive CLV model is claimed.

## 7. `run_post_load_pipeline.py`

### Purpose

`run_post_load_pipeline.py` is the repeatable post-MySQL refresh script. It reads the existing MySQL tables, validates critical relationships, regenerates the analytics extracts, writes validation results, and records a run-status JSON file.

It is the main automation used after a future prepared batch has been manually appended to MySQL.

### What it does not do

It does not:

- read or upload raw files;
- generate prepared files;
- append or modify MySQL tables;
- create database tables or migrations;
- create Power BI views;
- open Power BI or click Refresh;
- fit a predictive CLV model.

### Path constants and table mapping

- `PROJECT_ROOT`: project root.
- `ANALYTICS_DIR`: `data/analytics`.
- `QUALITY_DIR`: `data/quality`.
- `TABLES`: maps DataFrame names to MySQL table names:
  - `orders` -> `orders`
  - `customers` -> `customers`
  - `items` -> `order_items`
  - `payments` -> `payments`
  - `reviews` -> `reviews`
  - `products` -> `products`
  - `sellers` -> `sellers`
  - `categories` -> `category_translation`

Geolocation is not read by this current post-load analytics script because the generated analytical outputs do not require it.

### Functions

#### `read_tables(database_url)`

Creates a SQLAlchemy engine, reads each mapped MySQL table with pandas `read_sql_table`, returns a dictionary of DataFrames, and disposes the engine in a `finally` block.

#### `validate_tables(tables)`

Runs fail-fast checks and returns counts for:

- orders, customers, items, payments, and reviews;
- duplicate order IDs;
- orders without customers;
- items without orders;
- items without products;
- items without sellers;
- invalid review scores outside 1–5.

Any non-zero relationship, duplicate, or score failure raises `ValueError` before analytics files are regenerated.

#### `build_analytics(tables)`

Creates the analytical outputs:

1. Converts date and numeric fields.
2. Filters orders to `order_status == 'delivered'`.
3. Aggregates item count, item revenue, and freight by order.
4. Aggregates payment total and payment count by order.
5. Joins those independent aggregates to customer and order data to form the order fact.
6. Calculates `item_plus_freight`.
7. Calculates RFM values per `customer_unique_id`.
8. Assigns quartile-based R, F, and M scores from 1 through 4.
9. Assigns descriptive segments: `high_value`, `regular`, `developing`, and `needs_attention`.
10. Assigns first-purchase cohorts and calculates month numbers, retained customers, cohort sizes, and retention rates.
11. Calculates delivery duration in days.
12. Creates transaction-level CLV inputs using item-plus-freight value.

It returns a dictionary containing the five analytics DataFrames.

#### `save_outputs(outputs, checks, batch_id)`

Writes the analytics CSVs to `data/analytics/`, writes `post_load_validation_summary.csv` to `data/quality/`, and writes a successful `post_load_pipeline_run.json` containing the batch ID, UTC completion time, output filenames, and validation counts.

#### `main()`

Parses the optional `--batch-id` argument, loads `.env`, reads `DATABASE_URL`, creates a timestamp batch ID when necessary, runs the read/validate/build/save sequence, and records a failed run JSON if any step raises an exception.

### Why it is needed

It makes the post-load refresh repeatable and safe. It ensures database relationships are checked before outputs are overwritten, prevents analytical totals from being multiplied by one-to-many joins, and leaves a machine-readable record of success or failure.

## 13. Important processing rules and limitations

- Raw files remain immutable inputs. Preparation writes copies under `data/prepared/`.
- Source nulls are not silently replaced. Approved derived analysis values are stored in separate fields.
- Valid zero payments and zero freight values remain zero.
- Product count imputations are recorded with flags and an imputation method.
- Order date corrections are recorded with source timestamps, prepared timestamps, flags, and reasons.
- `customer_unique_id` is required for person-level repeat-customer, RFM, and cohort analysis.
- Item and payment aggregations must remain separate before order-level joins.
- The selected dataset is biased toward repeat customers and is not representative of the full Olist population.
- The CLV output is a transaction extract only. It is not predictive CLV.
- Notebook outputs can become stale. Re-run the relevant notebook or the repeatable script after data changes.
- The post-load script validates a subset of relationships before rebuilding outputs. Full preparation and load QA remains documented under `data/quality/`.
